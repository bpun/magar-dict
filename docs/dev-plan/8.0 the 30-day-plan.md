WEEK 1: Requirements, Language Data, and Database (Days 1–7)

Day 1: Requirements and project foundation

Write docs/requirements.md: personas (learner, admin, guest), user stories, the permission matrix from Section 1, and non-functional targets (search under 150 ms p95, WCAG 2.1 AA, 99.5% uptime goal).
Create the repo with the structure in Section 6. Initialize Git and add a .gitignore for .env, .venv, and data/raw/ if it contains licensed files.
Set up pyproject.toml, pre-commit with ruff, black, and mypy, and .env.example.
Deliverable: Repo skeleton, passing pre-commit hooks, and the requirements document.

Day 2: Language scope and governance

Choose one dialect for v1 and document it in docs/language_scope.md. Magar varieties differ, so label the choice clearly.
Choose the script (Devanagari, romanized, or both). Store both forms in the schema from the start.
Write docs/governance.md: who may verify words (native speakers), who may approve AI content (named admins), and how disputes are handled.
Contact community organizations and speakers. Get written permission for any word data you use.
Deliverable: Scope and governance documents, plus signed permission records.

Day 3: Data collection and source tracking

Gather word lists from permitted sources into data/raw/. Never edit raw files by hand.
Record every source in data/SOURCES.md: name, author, license, date obtained, and permission status.
Deliverable: At least 200 raw entries, each traceable to a source.

Day 4: Cleaning pipeline (scripts/import_words.py)

Load CSV or Excel files with pandas. Strip whitespace, normalize Unicode with unicodedata.normalize("NFC", text), and remove duplicates on the (magar, part of speech) pair.
Map part-of-speech labels to a controlled vocabulary (noun, verb, adjective, and so on).
Generate a URL slug for each word from its romanized form, with a numeric suffix when slugs collide.
Set every imported record to status = DRAFT. Nothing is public at import time.
Deliverable: data/processed/words.json and a log of every transformation applied.

Day 5: Validation (scripts/validate_data.py)

Enforce required fields, non-empty English glosses, valid part-of-speech tags, and the source-license requirement.
Output a report with error and warning levels. Block the pipeline on errors and allow warnings to pass.
Add a sample-review step: a native speaker checks a random 5% of entries each batch.
Deliverable: Validation report with zero critical errors and a reviewer sign-off.

Day 6: Database models and migrations

Implement the tables in Section 5 with SQLAlchemy 2.0 typed models: users, words, senses, examples, sources, user_word_progress, ai_generations, audit_log, refresh_tokens, and user_favorites.
Add indexes on words.slug, words.romanized, words.status, and user_word_progress.due_date.
Initialize Alembic and generate the first migration. Run Postgres locally with Docker Compose.
Deliverable: Schema migrated to Postgres and SQLite test database.

Day 7: Loading data and Week 1 review

Write scripts/load_words.py to insert validated data in one transaction, with a dry-run mode.
Create scripts/create_admin.py so the first admin is created from the command line, never through a public form.
Spot-check 20 random words in the database. Hold a retrospective and update the risk register.
Deliverable: Populated database, one admin account, and the Week 1 review notes.
WEEK 2: Backend API, Authentication, and Authorization (Days 8–14)

Day 8: Application core

Build the app factory in main.py. Add request-ID middleware, structured JSON logging with structlog, and a consistent error format: {"error": {"code", "message", "request_id"}}.
Add security-header middleware: Content-Security-Policy, Strict-Transport-Security, X-Content-Type-Options, Referrer-Policy.
Expose GET /health (checks the database and Redis) and confirm /docs loads.
Deliverable: Running app in Docker Compose with health checks passing.

Day 9: Public read API (no login)

GET /api/v1/words?letter=&page=&size=: paginated browse, published words only.
GET /api/v1/words/{slug}: details with senses and approved examples.
Add Cache-Control headers so public responses can be cached at the CDN.
Write tests confirming that drafts and archived words return 404 to guests.
Deliverable: Public endpoints with tests proving guests can’t see unpublished content.

Day 10: Search API (no login)

GET /api/v1/search?q=: prefix matching plus PostgreSQL full-text search over the Magar, romanized, and English fields.
Add typo tolerance with rapidfuzz over the top candidates.
Cache popular queries in Redis for 10 minutes.
Return a ranked list with a highlight snippet for each match.
Deliverable: Search under 150 ms p95 on the sample data, measured with a load script.

Day 11: Registration, email verification, and login

POST /api/v1/auth/register: validate password strength, hash with Argon2, send a verification email with a signed token that expires in 24 hours.
POST /api/v1/auth/login: return a 15-minute access token and a refresh token stored as a hash in refresh_tokens.
Lock login for 15 minutes after 5 failed attempts per email, tracked in Redis.
Deliverable: Full auth flow tested, including lockout and expired-token cases.

Day 12: Token refresh, logout, and password reset

POST /api/v1/auth/refresh: rotate the refresh token. Reusing an old token revokes the whole token family, which signals possible theft.
POST /api/v1/auth/logout revokes the current token. Password change revokes all sessions.
Password reset: request endpoint always returns the same response, so it doesn’t reveal which emails are registered.
Deliverable: Token lifecycle tests, including the reuse-detection path.

Day 13: Role-based access control

Implement get_optional_user, get_current_user, and require_role as shown in Section 7.
Build the admin user API: list and search users, change role, disable or enable accounts. Every change writes to audit_log.
Add a guard so the last active admin can’t be demoted or disabled.
Deliverable: A permission test matrix covering every endpoint × every role. All cases must pass.

Day 14: Week 2 review and coverage

Test the learner endpoints (favorites, profile) for authentication requirements.
Get coverage to at least 80% on core/, services/, and api/.
Run bandit and pip-audit and fix any high-severity findings.
Deliverable: Green test suite, coverage report, and a security scan with no high-severity issues.
WEEK 3: Word Management, Learning Features, and AI (Days 15–21)

Day 15: Admin word management API

POST /api/v1/admin/words, PATCH /api/v1/admin/words/{id}, DELETE (soft delete), and GET with filters for status, POS, and author.
Use optimistic locking through the version field. A stale update returns 409 Conflict.
Every write records a before/after diff in audit_log.
Deliverable: Admin CRUD with conflict handling and full audit trail.

Day 16: Status workflow (services/word_workflow.py)

Implement the state machine from Section 1 as an explicit transition table. Invalid transitions raise an error.
Learners can submit a correction. It creates a NEEDS_REVIEW revision and doesn’t change the live entry.
Admins approve, reject with a reason, or publish.
Deliverable: Workflow tests covering every valid and invalid transition.

Day 17: Embeddings and vector index (scripts/build_embeddings.py)

Load LaBSE with sentence-transformers. Embed each word’s English gloss, Nepali gloss, and romanized form.
Build a FAISS index with normalized vectors for cosine similarity, and store the ID mapping beside it.
Version the index (index_v{date}). The app loads the active version from settings, so rollback is a config change.
Deliverable: Versioned index files and a rebuild script that runs in under 5 minutes on sample data.

Day 18: Semantic and hybrid search

Add mode=semantic and mode=hybrid to the search endpoint.
Filter by publication status after retrieval. Over-fetch (for example, 3× the page size) so filtering doesn’t leave too few results.
Combine keyword and semantic rankings with reciprocal rank fusion.
Write an evaluation set of 30 queries with expected answers. Report precision@5 for each mode.
Deliverable: Hybrid search plus an evaluation report comparing the three modes.

Day 19: AI service layer (services/ai/)

Define an LLMProvider interface with one method for structured generation. Write an OpenAI adapter and a test double so the tests never call a real API.
Write versioned prompt templates in prompts/. Each prompt includes only verified glosses and approved examples as context, and it forbids inventing forms not present in the data.
Validate every model response against a Pydantic schema. Reject and log malformed output without retrying more than once.
Record each call in ai_generations with the prompt version, model name, and token cost.
Deliverable: AI service with mocked tests, schema validation, and cost logging.

Day 20: AI endpoints with quotas and review

POST /api/v1/ai/explain/{word_id} and POST /api/v1/ai/examples/{word_id} require a logged-in user. Learners get 20 generations per day, enforced in Redis, and admins are exempt.
Every generated item is saved as NEEDS_REVIEW and is invisible to the public until an admin approves it.
Cache by (word, kind, prompt version, model), so repeated requests cost nothing.
Admin review queue: GET /api/v1/admin/review, then approve, edit-and-approve, or reject.
Deliverable: Quota enforcement, cache hits verified in tests, and the review queue working end to end.

Day 21: Audio and Week 3 review

scripts/generate_audio.py creates audio per word and uploads it to the object store. Store the key in words.audio_key.
GET /api/v1/words/{slug}/audio returns a redirect to a signed URL, which keeps the storage bucket private.
Label audio as “approximate pronunciation” until native recordings replace it, and store a source field for each recording.
Run the Week 3 review: check API performance, AI costs so far, and the review queue backlog.
Deliverable: Audio endpoint, cost report, and Week 3 retrospective.
WEEK 4: Web Interface, Mobile App, Hardening, and Launch (Days 22–30)

Day 22: Public web shell and search page

Build base.html with the Tailwind navbar, search box, and footer. The navbar shows a “Log in” button for guests and an account menu for logged-in users.
Search page uses HTMX for live results: hx-get="/search" hx-trigger="input changed delay:300ms" hx-target="#results".
Use the Noto Sans Devanagari web font with font-display: swap.
Deliverable: Public search page that works without an account.

Day 23: Public word detail page and SEO

Route /words/{slug} renders the word, senses, approved examples, and audio button.
Guests see a call to action: “Log in to generate more examples.”
Add meta tags, canonical URLs, and JSON-LD DefinedTerm markup so the entries can be indexed.
Generate sitemap.xml from published words only.
Deliverable: Indexable, shareable word pages with valid structured data.

Day 24: Auth pages and CSRF protection

Register, login, verify email, forgot password, and reset password pages.
Add CSRF tokens to every form that changes state. Use SameSite=Strict cookies.
Show clear error messages without revealing whether an email exists.
Deliverable: Full account flows in the browser, tested with Playwright.

Day 25: Learner experience

Dashboard: streak, words learned, due count, and a Chart.js progress graph.
Daily review session: flip cards with Again, Hard, Good, and Easy buttons mapped to SM-2 quality scores. HTMX loads the next card without a page reload.
Favorites and personal notes, kept private to each user.
Deliverable: A learner can complete a full review session and see progress update.

Day 26: Admin dashboard

Overview: total published words, pending reviews, active users, and AI spend this month.
User management table with search, role toggles, and disable buttons. Each action requires a confirmation dialog.
Word editor form with inline validation, a preview of how the entry will look to guests, and a status selector limited to valid transitions.
Review queue screen with side-by-side AI output and the original entry.
CSV import page: upload, run validation, preview errors, then confirm.
Deliverable: Admins can manage users, words, reviews, and imports from the browser.

Day 27: Progressive Web App for mobile

manifest.json with name, icons (192 and 512 px), theme color, and display: standalone.
Service worker caches the app shell, the Devanagari font, and the last 200 public words viewed.
The service worker never caches authenticated or admin responses, and it clears cached data on logout.
Show a custom “Install app” prompt on Android. On iOS, show instructions for “Add to Home Screen.”
Deliverable: App installs on Android and iOS, and public words open offline.

Day 28: Security hardening, accessibility, and testing

Run OWASP ZAP against staging and fix findings above low severity.
Test a Content Security Policy in report-only mode, then enforce it.
Accessibility audit: color contrast (4.5:1 minimum), keyboard navigation, ARIA labels, and screen reader testing with VoiceOver or NVDA.
Run Playwright end-to-end tests for three journeys: guest search, learner review session, and admin publishing a word.
Test on a 360 px wide screen.
Deliverable: Security scan report, accessibility report, and passing E2E suite.

Day 29: CI/CD and deployment

GitHub Actions pipeline: lint, type check, unit and API tests, E2E tests, Docker build, bandit, pip-audit, and deploy on merge to main.
Deploy to Render or Fly.io with managed Postgres and Redis. Set DATABASE_URL, JWT_SECRET, LLM_API_KEY, and SMTP credentials as platform secrets, never in code.
Run Alembic migrations as a deploy step and make them reversible.
Enable HTTPS, a custom domain, and automated daily database backups with a tested restore.
Set up separate staging and production environments.
Deliverable: Staging and production URLs, a working pipeline, and a documented restore test.

Day 30: Monitoring, documentation, beta feedback, and launch

Connect Sentry for errors and set alerts for error-rate spikes. Set up an uptime monitor on /health. Add a dashboard for AI cost and quota usage.
Write docs/runbook.md: how to rotate secrets, rebuild the search index, roll back a release, and handle a data-correction request.
Publish docs/privacy-policy.md and terms of use. Add account deletion and data export endpoints, since learners’ personal data is stored.
Triage feedback from the beta group (run during Days 27–29) and fix blocking issues.
Launch to the Magar community. Publish the README with setup, architecture, the contribution process, and how to report a wrong entry.
Deliverable: Launched v1.0, with a runbook, privacy policy, and a v2 roadmap: native recorded audio, offline sync for learners, a Flutter native app, and an editor role for trusted community contributors.
